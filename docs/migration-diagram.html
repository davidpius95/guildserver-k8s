PHASE 01

The sequencing decision

The instinct was to decouple storage first, then move compute. That ordering is wrong — and understanding why is the single most consequential design call in the project.
✕ Decouple storage first
  1. Build the replacement storage tier on Guild-A's constrained 337 GB Ceph
  2. Migrate 6 volumes onto it
  3. Migrate VMs, now dragging the new storage disks across the wire too

Builds the escape route inside the thing being escaped, and doubles the data that has to cross the network.

✓ Migrate compute first
  1. Live-migrate the 3 VMs to Guild-B
  2. Build storage on Guild-B's terabytes of local-lvm
  3. Copy volumes across — Guild-A's Ceph is still readable over the shared L2

Same destination, far less risk, and the copy happens live inside one cluster instead of between two.

Architectural principle

The temporary cross-cluster dependency isn't a flaw to be designed out — it is the bridge that makes an online data migration possible. You read from the old storage and write to the new one, live, within a single cluster. A temporary dependency that enables an online cutover is worth more than architectural purity that forces an outage.

PHASE 02

Live VM migration

Proxmox has no native cross-cluster live migration in the clustered sense. Both sides ran PVE 9.2, which exposes an experimental remote_migrate API supporting online transfer.

Control plane — different rules

k8s-cp-1 was deliberately not drained. It carries a NoSchedule taint and hosts only static pods (etcd, apiserver, scheduler, controller-manager, kube-vip) plus DaemonSets. Static pods are kubelet-managed and cannot be evicted — draining would have churned CoreDNS for no benefit. One genuine advantage here: single-member etcd has no quorum election to disrupt during the cutover pause; it simply resumes.

PHASE 03

Storage decoupling

Compute now lived on Guild-B while all six volumes still resolved to Guild-A's Ceph monitors. The bridge worked exactly as designed — and had to be dismantled deliberately.
Engine choice Longhorn · 2 replicas Replicated across the workers' own disks. Rejected: local-path (no replication), Rook-Ceph (far too heavy for 2-core / 6 GB workers).
Constraint Two schedulable nodes The control plane is tainted, so replicaCount: 2 is the hard ceiling — documented as a known limitation, not hidden.
Constraint PVC class is immutable A volume cannot change StorageClass. It must be recreated and its contents copied — names kept identical so manifests barely changed.
Method Smallest blast radius first A 1 GiB volume was migrated end-to-end before any production data. It exposed four distinct failure modes.

PHASE 04

What actually went wrong

Every one of these was found by verifying rather than assuming. Several would have caused silent data loss if the happy path had been trusted.
01 · Silent failure

GitOps reverted the migration

The test migration appeared to succeed — checksum matched. In reality ArgoCD had reverted the patch within seconds and the pod was still mounting the old Ceph volume. The matching checksum was reading the source, not the destination: a false positive that would have "verified" a migration that never happened.

ResolutionChange the class in Git first, via reviewed PR. Suspend auto-sync on the root app then the child — order matters — and verify the suspension holds for 30 s before proceeding.

02 · Resource lifecycle

Completed Jobs pinned PVCs

delete pvc hung indefinitely; the volume sat Terminating. A finished Job pod still held the pvc-protection finalizer — a completed pod is still a consumer.

ResolutionDelete the Job the moment it completes, before touching the PVC. Encoded into the reusable script.

03 · Data-loss near miss

A racing pod repopulated the volume

Multi-Attach error — the app pod grabbed the fresh empty PVC before the copy job could. Worse: that app's seed initContainer writes new content if the volume is empty, which would have overwritten the migrated data and destroyed the exact timestamp being preserved.

ResolutionHold the workload at zero replicas for the entire window — not merely at the start.

04 · Self-inflicted

A hidden installer failure

Copy jobs died with rsync: not found. The worker nodes have no outbound egress so the package install failed — but the failure was invisible because the output had been redirected to /dev/null. Tidy logs turned a loud failure into a confusing one.

ResolutionUse cp -a, built into the image, no network required. Never silence installer output.

05 · Control hierarchy

The Operator outranked the StatefulSet

Scaling the Prometheus StatefulSet to zero appeared to work — then the pod returned and pinned the PVC. The Prometheus Operator reconciles replicas from the Prometheus CR, so editing the StatefulSet is meaningless.

ResolutionScale via the custom resource. With operator-managed workloads, find the real source of truth — there is often a controller above the object you're editing.

06 · API immutability

StatefulSet claim templates are frozen

ArgoCD failed repeatedly: updates to statefulset spec … are forbidden. Changing the storage class meant changing volumeClaimTemplates, which Kubernetes forbids on an existing StatefulSet.

Resolutiondelete sts --cascade=orphan — removes the controller, leaves pods and PVCs intact — then let GitOps recreate it. It correctly re-adopted the already-migrated volume.

07 · Misleading health

ArgoCD gave up, and stayed given-up

Loki's StatefulSet was never recreated and Loki wasn't running at all — yet the application reported Healthy. ArgoCD had exhausted 5 retries against the immutable field an hour earlier and backed off; nothing re-triggered it.

ResolutionManual sync. Caught only because the pod list was checked directly. Aggregate status can be green while a component is entirely absent.

08 · Config drift

A merged Git change never applied

After the PR set ceph-rbd to non-default, the cluster still had it as the default StorageClass — that manifest isn't reconciled by any ArgoCD app. Any new PVC without an explicit class would have silently provisioned straight back onto Guild-A's Ceph.

ResolutionFix at the cluster level too. "It's in Git" is not "it's applied" — know which paths are reconciled and which are documentation.

09 · Design flaw found

A circular backup dependency

Velero backed up to a MinIO pod inside the cluster, whose own data sat on a PVC in that same cluster. It could never have restored itself. Separately: Velero had run for over a week with zero backups and no schedule — healthy, validating, doing nothing.

ResolutionMinIO redeployed to Guild-A — a separate failure domain — plus a daily schedule, proven with a real 20/20-item backup and bytes confirmed on disk.

10 · Tooling trap

A CRD short-name collision

A polling loop watched a backup for minutes and saw nothing. kubectl get backup resolves to backups.longhorn.io, not Velero's — both CRDs claim the short name, and the wrong resource was returned silently.

ResolutionAlways qualify: backups.velero.io. Recorded in the repo so the next person loses zero minutes to it.

11 · Infrastructure

A wedged hypervisor agent

The QEMU guest agent stopped responding mid-operation. A guest-side service restart was insufficient — the virtio-serial channel required a full VM stop/start, not a reboot.

ResolutionDiagnosed by sampling /proc/net/dev over 5 s: ~2 KB/s proved a transfer was hung rather than slow, converting an open-ended wait into a decision.

PHASE 06

Engineering principles applied
Reversibility at every stepMigration ran with delete unset, retaining every source VM stopped. At no point did the plan contain a step that could not be undone.
Smallest blast radius firstA 1 GiB test volume surfaced four distinct failure modes that would have been considerably more damaging discovered on 8–10 GiB production data.
Verify the thing, not the statusArgoCD reported Healthy while Loki did not exist. A checksum matched while reading the wrong volume. Every claim was checked against primary evidence — API responses, bytes on disk, HTTP probes from independent hosts.
Order by criticalityWorkers before control plane. Non-GitOps apps before GitOps ones. The backup target last, because everything else might need restoring.
Name the trade-offsTwo-replica Longhorn has no rebuild headroom. Backups are same-site. Both are recorded in the repository as known limitations rather than quietly omitted.
Automate once provenAfter the manual test, the sequence was encoded into a reusable script handling every discovered failure mode — then applied uniformly to the remaining five volumes.
PHASE 07

Known limitations & next steps

Stated plainly. A migration record that claims no residual risk isn't a record, it's marketing.
2-replica LonghornTwo schedulable workers means no spare node to rebuild onto. Add a third worker → 3 replicas.
Backups are same-siteBoth clusters share a LAN and a building. Replicate the bucket to genuinely off-site object storage.
Single control planeOne node, single-member etcd. Stack to three control-plane nodes for real HA.
Restore not drill-testedBackups complete and verify, but a full restore has not been rehearsed. Schedule a drill.
Stale source VMsVMs 120–122 remain stopped on Guild-A. Starting one causes an IP conflict — delete once confidence is established.
Orphaned Ceph poolk8s-rbd still holds ~22.8 GB raw. Drop the pool to reclaim it.
